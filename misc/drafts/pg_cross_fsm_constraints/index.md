## Enforcing Cross-FSM Constraints in Postgres

Suppose you've got multiple independent DB-based state machines and you have to
coordinate state changes across them and keep them consistent. Specifically, a
transition in one state machine necessitates a transition in another.

For example, consider the following:

- We're managing an e-commerce system
- We've got FSMs for orders, payments and shipping:

- Payment can only be initiated if an order is confirmed (e.g. we have to
  confirm that all the items in the order are in our inventory before charging
  the customer)
- Shipment can only start once payment has succeeded
- Order moves to 'paid' once payment has succeeded
- Order moves to 'shipped' once the shipment is shipped
- Order moves to 'delivered' once the shipment is delivered
- Refund triggers payment refund AND order state change
- Refund requires the following:
  - order moves from delivered to refunded
  - payment moves from succeeded to refunded
- and so on,

For this post, we'll focus on two cases for the sake of brevity, both of which
entail interaction and coordination between orders and payments:

1. Payment initiation **requires** that the order is confirmed
2. Order is in state 'paid' _if and only if_ payment succeeded

For both cases, we'll proceed as follows (this is the solution I came up with,
open to suggestions):

- enforce cross-FSM constraints/guards within Postgres via SQL guards
- use durable workflows to orchestrate orders + payments i.e. coordinate within
  the application rather than within Postgres

Let's start with the first case: "payment initiation requirs order
confirmation". To create a payment, we need the order ID and amount:

```sql
create table payments(
    id bigint primary key generated by default as identity,
    order_id bigint not null references orders(id),
    amount numeric(12,2) not null,
    metadata jsonb default '{}',
    created_at timestamptz not null default now()
);
```

Here's the `before insert` trigger that enforces valid FSM transitions for
payments:

```sql
create function payment_events_trigger_func()
returns trigger
language plpgsql
as $$
declare
  current_state payment_state;
  next_state payment_state;
begin
    -- lock the parent payment row which always exists
    perform 1 from payments where id = NEW.payment_id for update;

    -- get current state
    select state into current_state
    from payment_events
    where payment_id = NEW.payment_id
    order by id desc
    limit 1
    ;

    -- if no prev event exists for this payment then we're in start state
    if current_state is null then
      current_state := 'start'::payment_state;
    end if;

    -- calculate the next state based on curr state and new event
    next_state := payment_transition(current_state, NEW.event);

    -- validate the transition
    if next_state = 'error'::payment_state then
        raise exception 'invalid payment event: % is not valid from state %',
        NEW.event, current_state;
    end if;

    -- automatically set the state s.t. users only need to provide the event
    NEW.state := next_state;
    return new;
end
$$
;
```

Now, towards the end we'll make the following addition which ensures order has
to be confirmed before we initiate payment:

```sql
create function payment_events_trigger_func()
returns trigger
language plpgsql
as
    $$
declare
  current_state payment_state;
  next_state payment_state;
  v_order_state order_state;
  v_order_id bigint;
begin
    -- original code

    -- addition:
    -- CROSS-FSM Guard: payment creation requires confirmed order
    if NEW.event = 'create' then
        -- get current state of order
        select p.order_id into v_order_id
        from payments p where p.id = NEW.payment_id;

        select oe.state into v_order_state
        from order_events oe
        where oe.order_id = v_order_id
        order by oe.id desc limit 1;

        if v_order_state is distinct from 'confirmed' then
            raise exception 'cannot create payment: order not confirmed (got: %)', v_order_state;
        end if;
    end if;

    NEW.state := next_state;
    return new;
end
$$
;
```

Now, the following will succeed:

```sql
-- create & confirm order 1
insert into orders(id, customer_id, total_amount)
values (1, 100, 2000);

insert into order_events(order_id, event) values
   (1, 'create'),
   (1, 'confirm');

-- initiate payment for order 1
insert into payments (id, order_id, amount)
select 1, id, total_amount
from orders
where id = 1;

insert into payment_events(payment_id, event) values
    (1, 'create');
```

We'll do the same for orders for the case where an order is paid iff payment
succeeded; we'll add the following guard in the `before insert` triggers for
order events:

```sql
create function order_events_trigger_func()
returns trigger
language plpgsql
as
    $$
declare
  current_state order_state;
  next_state order_state;
  v_payment_state payment_state;
begin
    -- initial code...

    -- addition:
    -- Cross-FSM Guard: check that the associated payment is in succeeded state
    if NEW.event = 'mark_paid' then
        select pe.state into v_payment_state
        from payments p
        join payment_events pe on pe.payment_id = p.id
        where p.order_id = NEW.order_id
        order by pe.id desc limit 1;

        if v_payment_state is distinct from 'succeeded' then
            raise exception 'cannot set order to paid: no succeeded payment (got: %)', payment_state;
        end if;
    end if;

    NEW.state := next_state;
    return new;
end
$$
;
```

Now a payment has to be successful:

```sql
insert into payment_events(payment_id, event) values
    (1, 'submit'),
    (1, 'succeed');
```

so that we can have `mark_paid` for an order:

```sql
insert into order_events(order_id, event) values
   (1, 'mark_paid');
```

As for orchestrating payments within the application, we'll use DBOS to handle
this part:

The process payment workflow gets the order_id and invokes the following steps:

1. Gets the order info
2. Ensures that the order is in state 'confirmed'
3. Creates the payment record and transitions it to 'processing'
4. Initiates the payment request to the payment processor
5. If initiating the payment fails, stop the workflow and return
6. Otherwise, wait for the processor to send the webhook with the payment
   status. The wait should have a timeout
7. If the payment succeeed, mark the order as paid

Here's the code for the workflow:

```python
@DBOS.workflow()
def process_payment_workflow(order_id, payment_method):
    # get order info
    order_info = get_order_info(order_id)
    if not order_info:
        raise ValueError(f"Order {order_id} not found")

    if order_info["state"] != "confirmed":
        raise ValueError(f"Order must be confirmed, got: {order_info['state']}")

    amount = order_info["total_amount"]

    # create payment record
    payment_id = create_payment_record(order_id, amount, payment_method)

    # publish payment_id for tracking
    DBOS.set_event(PAYMENT_ID, payment_id)

    # payment FSM
    insert_payment_event(payment_id, "create")  # move from start to pending
    insert_payment_event(payment_id, "submit")  # move from pending to processing

    # build callback URL with workflow_id so webhook knows where to send result
    callback_url = f"{WEBHOOK_BASE_URL}/webhook/payment/{DBOS.workflow_id}"

    # initiate payment (CHECKPOINTED - won't re-initiate on recovery)
    init_result = initiate_payment_request(
        payment_id, payment_method, amount, callback_url
    )

    if not init_result.get("initiated"):
        # failed to initiate, mark as failed
        insert_payment_event(payment_id, "fail")
        final_result = {
            "payment_id": payment_id,
            "success": False,
            "transaction_id": None,
            "failure_reason": f"Failed to initiate: {init_result.get('error')}",
        }
        DBOS.set_event(PAYMENT_RESULT, final_result)
        return final_result

    # wait for webhook
    # - if the app crashes here, on restart DBOS.recv() continues waiting
    # - the webhook can still call DBOS.send() and the workflow will receive it
    # - no initiated payment is lost
    # ═══════════════════════════════════════════════════════════════════════════
    webhook_result = DBOS.recv(PAYMENT_WEBHOOK, timeout_seconds=PAYMENT_TIMEOUT)

    if webhook_result is None:
        # timeout - no webhook received
        insert_payment_event(payment_id, "expire")
        final_result = {
            "payment_id": payment_id,
            "success": False,
            "transaction_id": None,
            "failure_reason": "Payment processor timeout",
        }
    elif webhook_result.get("success"):
        # payment succeeded
        DBOS.logger.info(f"Payment {payment_id} succeeded via webhook")
        insert_payment_event(payment_id, "succeed")

        # order FSM: confirmed -> paid (guard checks payment succeeded)
        insert_order_event(order_id, "mark_paid")

        final_result = {
            "payment_id": payment_id,
            "success": True,
            "transaction_id": webhook_result.get("transaction_id"),
            "failure_reason": None,
        }
    else:
        # payment failed
        insert_payment_event(payment_id, "fail")
        final_result = {
            "payment_id": payment_id,
            "success": False,
            "transaction_id": None,
            "failure_reason": webhook_result.get("failure_reason"),
        }

    DBOS.set_event(PAYMENT_RESULT, final_result)
    return final_result
```

Ok, we've enforced cross-entity constraints at the DB level and to some extent
at the application level (`if order_info["state"] != "confirmed":`). We've also
used DBOS to handle cross-entity workflows at the application level.

Why DBOS:

- provides durable execution with minimal friction
- checkpoints steps and handles workflow recovery
- no additional infrastructure, uses PG

There's probably other approaches, if you've got one, please do suggest.
